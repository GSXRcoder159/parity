## Triage (2026-10-03)

**Not API drift.** Of the 9 train rows, 8 are the same v1.6 limitation as 2026-10-02 (one calendar month plus a fixed time, on sequences last recorded on 2026-09-28). The other one is a normalization gap not seen before: a currency conversion in an error message. Every response that reports a `Stripe-Version`, in both recordings of every compared train sequence, carries the same one (2026-08-26.dahlia), and no status, error code or field set changed.

- **One month plus 72 h (6 rows):** clock-period-rollover (#5, #12, #19, all monthly). The renewal invoice's `automatically_finalizes_at`, `effective_at`, `status_transitions.finalized_at` and `status_transitions.paid_at`, and the clock's `frozen_time` and `status_details.advancing.target_frozen_time` after the second advance: `+792h` from a September start against `+816h` from an October one, exactly 72 h past one calendar month in both recordings.
- **One month plus 1 h (2 rows):** `next_payment_attempt` before any attempt, on the rollover's renewal draft and on invoice-preview-proration's preview (#1, #8). `+721h` against `+745h`, 1 h past one calendar month in both.
- **Currency conversion in an error message (1 row, `POST /v1/payment_intents`, boundaries-amounts #5, `$.error.message`):** the `amount_too_small` refusal of a payment intent below the minimum, in a currency other than USD. Status, error code and the message's wording are the same in both recordings. The message ends with the amount's approximate value in USD, which Stripe converts at the current exchange rate, and the rounded figure moved by one cent between 2026-09-28 and tonight. The other such message in tonight's slice, and the one in 2026-10-02's, did not change. Nothing in v1.6 rewrites the converted figure, so this row will come back whenever the rate moves it. A rule that writes the figure as an opaque value would hide a wrong conversion, so it belongs in a normalization version that states it, not in this triage.
