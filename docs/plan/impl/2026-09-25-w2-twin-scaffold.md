# Implementation plan: Parity twin scaffold (W2)

Spec (authority): `docs/plan/2026-09-25-parity-mvp-plan.md` §2.1, §3.2, §5 W2. Binding decisions: `docs/decisions/0001-clean-room-and-legal-gate.md` (clean room, naming), `docs/decisions/0002-twin-architecture-and-rolling-oracle.md` (code + data split, scaffold honesty rules, `Parity-Now`).
Sandbox behavior knowledge: `docs/plan/impl/templates-validation.md`. Contract types: `src/types.ts` (`StripeEvent`).

## Global Constraints

- TypeScript run directly by Node ≥22.18 (type stripping, no build step). Relative imports use explicit `.ts` extensions; type-only imports use `import type`. `npx tsc -p tsconfig.json` must pass. Tests: `node --test test/*.test.ts` (`node:test`, `node:assert/strict`); twin tests call the in-process handler or a server on an ephemeral port — no network beyond localhost.
- No new runtime dependencies (`node:http`, `node:crypto` only). Dev dependencies only with a stated reason.
- **Clean room (0001):** behavior derives from the MIT OpenAPI spec (pinned: `https://raw.githubusercontent.com/stripe/openapi/2bab97685e29abae0c241680c2257153e259e50f/latest/openapi.spec3.json`, API version `2026-08-26.dahlia`, MIT notice kept next to the vendored file), from public Stripe docs, and from our own sandbox observations. No code from localstripe (GPL) or any other twin. The word "Stripe" never appears in a product/package/page name; use "the Stripe API" in prose, never possessive/plural forms.
- **Scaffold honesty (0002 §4):** object templates are generated from the spec with generic defaults — never hand-copy observed field values into `src/twin/shapes/`. Error catalog entries carry real `status`/`type`/`code`/`param` (semantics) but `message` = `"parity: <key>"`. Statuses, event sets and state transitions may follow observations.
- Pinned API version: every response carries header `Stripe-Version: 2026-08-26.dahlia` (echo the request's `Stripe-Version` if it is that value; other values are accepted and echoed but behavior stays dahlia).
- Do not edit `src/cli.ts`, `src/bench/*`, `templates/*` (another workflow owns them). `src/types.ts` only if unavoidable, listed under concerns.
- Minimal code (ponytail); mark ceilings with `// ponytail:`. Commits per task, message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; stage only your paths; retry on `index.lock`.

## Task 1: Pruned spec and generated object templates

**Paths:** `scripts/prune-spec.ts`, `scripts/gen-shapes.ts`, `src/twin/spec/openapi.pruned.json`, `src/twin/spec/LICENSE-stripe-openapi`, `src/twin/spec/README.md`, `src/twin/shapes/*.json`, `test/twin-shapes.test.ts`

- `scripts/prune-spec.ts`: download the pinned spec (URL above) to a temp file, keep only these operations and every component schema they reference transitively, write `src/twin/spec/openapi.pruned.json` (pretty-printed, deterministic key order), and record the source URL + commit SHA + API version in `src/twin/spec/README.md`. Copy the MIT LICENSE text from the same commit to `src/twin/spec/LICENSE-stripe-openapi`.
  In-scope operations (method path): customers `POST/GET /v1/customers`, `GET/POST/DELETE /v1/customers/{customer}`, `GET /v1/customers/search`, `GET /v1/customers/{customer}/payment_methods`; payment methods `GET /v1/payment_methods`, `GET/POST /v1/payment_methods/{payment_method}`, `POST /v1/payment_methods/{payment_method}/attach`, `POST /v1/payment_methods/{payment_method}/detach`; products `POST/GET /v1/products`, `GET/POST /v1/products/{id}`; prices `POST/GET /v1/prices`, `GET/POST /v1/prices/{price}`; subscriptions `POST/GET /v1/subscriptions`, `GET/POST/DELETE /v1/subscriptions/{subscription_exposed_id}`; invoices `GET /v1/invoices`, `GET /v1/invoices/{invoice}`, `POST /v1/invoices/create_preview`, `POST /v1/invoices/{invoice}/pay`, `POST /v1/invoices/{invoice}/void`, `POST /v1/invoices/{invoice}/finalize`; payment intents `GET /v1/payment_intents`, `GET /v1/payment_intents/{intent}`; charges `GET /v1/charges`, `GET /v1/charges/{charge}`; refunds `POST/GET /v1/refunds`, `GET /v1/refunds/{refund}`; events `GET /v1/events`, `GET /v1/events/{id}`; webhook endpoints `POST/GET /v1/webhook_endpoints`, `GET/POST/DELETE /v1/webhook_endpoints/{webhook_endpoint}`; test clocks `POST/GET /v1/test_helpers/test_clocks`, `GET/DELETE /v1/test_helpers/test_clocks/{test_clock}`, `POST /v1/test_helpers/test_clocks/{test_clock}/advance`. (Use the exact path-parameter names the spec uses; the ones above are indicative.)
- `scripts/gen-shapes.ts`: for every component schema in the pruned spec that has `x-resourceId` (plus `deleted_customer` and `deleted_webhook_endpoint` if present), write `src/twin/shapes/<x-resourceId>.json` = a template object containing **only the schema's `required` properties**, with generic defaults: `object` → the resourceId constant (from the schema's `object` enum); `livemode` → `false`; `id` → `""`; nullable (`nullable: true`) → `null`; boolean → `false`; integer/number → `0`; string enum (non-nullable) → first enum value; string → `""`; array → `[]`; `anyOf` with a string branch and a `$ref` branch (expandable) → the string form (`""`, or `null` if nullable); object with `properties` → recurse with the same rules (depth limit 3, deeper → `{}`); `additionalProperties` maps (e.g. `metadata`) → `{}`. Keys sorted alphabetically. Deterministic output.
- Both scripts are re-runnable (`node scripts/prune-spec.ts && node scripts/gen-shapes.ts`) and idempotent.
- Tests: pruned spec contains every in-scope operation; `customer.json`, `subscription.json`, `invoice.json`, `price.json`, `refund.json`, `event.json`, `payment_method.json`, `charge.json`, `payment_intent.json`, `webhook_endpoint.json` exist; `customer.json.object === "customer"`, `livemode === false`, `metadata` is `{}`; an expandable field (e.g. `subscription.customer`) is a string, not an object; running the generator twice yields identical files.

## Task 2: Twin core

**Paths:** `src/twin/server.ts`, `src/twin/form.ts`, `src/twin/store.ts`, `src/twin/list.ts`, `src/twin/expand.ts`, `src/twin/validate.ts`, `src/twin/errors.ts`, `src/twin/errors.json`, `src/twin/build.ts`, `src/twin/resources/events.ts`, `test/twin-core.test.ts`
**Depends on:** Task 1.

- `form.ts`: `parseForm(body: string): Record<string, unknown>` — inverse of the harness's `encodeForm`: `a[b][0][c]=x` → `{a:{b:[{c:"x"}]}}`, `expand[]=x&expand[]=y` → `{expand:["x","y"]}`, values stay strings, empty string preserved (`""` means unset). Also used for GET/DELETE query strings.
- `build.ts`: `build(type: string, fields: Record<string, unknown>): Record<string, unknown>` = deep clone of `shapes/<type>.json` shallow-merged with `fields` (fields win; key order irrelevant). Unknown type → throw.
- `store.ts`: in-memory event-sourced store. `events: StripeEvent[]` (append-only), `objects: Map<string, object>`, `deleted: Map<string, object>` (tombstones), `idem: Map<string, {hash, status, body, at}>`. `apply(emits, meta)`: each emit `{ type, object, previous_attributes? }` becomes a full event (`id: evt_…`, `object: "event"`, `api_version: "2026-08-26.dahlia"`, `created: now`, `data: {object, previous_attributes?}`, `livemode: false`, `pending_webhooks` (number of matching enabled webhook endpoints), `request: {id: requestId, idempotency_key}`, `type`) and updates the projection `objects.set(object.id, object)`. A handler may also return `puts` (objects saved without an event) and `deletes` (ids to tombstone, with the tombstone body). `reset()` clears everything (<50 ms). `snapshot()` for `/_parity/state`.
- `errors.ts` + `errors.json`: catalog `key → { status, type, code?, param?, message }`, `message` may contain `{placeholders}`; `class TwinError`; `fail(key, vars?)` throws it. Server renders `{ error: { type, code?, param?, message, doc_url? (https://stripe.com/docs/error-codes/<code> when code), request_log_url: "https://dashboard.stripe.com/test/logs/<requestId>" } }`. Seed the catalog with generic keys the core needs: `unrecognized_url` (404 invalid_request_error), `api_key_missing` (401), `api_key_invalid` (401), `parameter_unknown` (400, code `parameter_unknown`, param = the param), `parameter_missing` (400), `parameter_invalid_integer` (400), `parameter_invalid_string`/enum (400, `parameter_invalid_string` or no code — pick what observations show), `resource_missing` (404, code `resource_missing`), `idempotency_mismatch` (400, type `idempotency_error`, no code), `expand_too_deep`/`expand_invalid` (400), `list_limit_invalid` (400). Messages per 0002 §4.3.
- `validate.ts`: validates a parsed request against the pruned spec's request schema for the matched operation: unknown parameters at any object depth whose schema lists `properties` → `parameter_unknown` with Stripe-style bracket param names (`items[0][foo]`); coerce form strings to the schema's type (integer, boolean, number); invalid integer → `parameter_invalid_integer`; invalid enum → the enum error key; `expand` always allowed. Returns the coerced params. Required-ness stays in handlers (the spec is incomplete on it).
- `list.ts`: `list(items, params, url)` → `{ object: "list", data, has_more, url }`: sort by `created` desc, ties by insertion order desc; `limit` default 10, valid 1–100 (else `list_limit_invalid`); `starting_after`/`ending_before` (unknown id → `resource_missing` with param); generic `created` filter (`created[gt|gte|lt|lte]` or exact). `search(items, query, url)` → `{ object: "search_result", data, has_more, next_page: null, url }` supporting `field:'value'`, `metadata['k']:'v'`, joined by ` AND `.
- `expand.ts`: apply `expand` paths to the response body: replace an id string at the dotted path with the stored object (for lists, paths start with `data.`); max depth 4 (deeper → `expand_too_deep`); a path that does not point at an expandable id → `expand_invalid`.
- `server.ts`: `createTwin(opts?) → { handle(req: {method, path, query, headers, body}): Promise<{status, headers, body}>, listen(port): Promise<http.Server>, store }`. Pipeline: auth (Bearer or Basic `key:`; accept keys starting `sk_test_` or `rk_test_`) → parse → route (table registered by resource modules: `[method, RegExp, handler, operationKey]`; unmatched → `unrecognized_url`) → validate → idempotency (POST only; key = header `Idempotency-Key`; hash of method+path+params; same → replay stored status/body with header `Idempotent-Replayed: true`; different params → `idempotency_mismatch`; the first result — including errors — is stored for 24 h) → handler `(ctx, req) → { status, body, emits?, puts?, deletes? }` (errors via `fail`) → store.apply → expand → headers `Request-Id: req_…`, `Stripe-Version`, `Content-Type: application/json`. `ctx` = `{ now(), id(prefix), get(id), all(type), requestId, fail, build }`. **Clock:** `now()` = header `Parity-Now` (unix seconds) when present, else wall clock. **IDs:** `prefix + "_" + 24 base62 chars` (14 for `cus`), cryptographically random.
- Parity endpoints (no auth): `POST /_parity/reset`, `POST /_parity/seed` (JSON `{objects: [...]}` → puts), `GET /_parity/state` (objects + event count).
- `resources/events.ts`: `GET /v1/events` (list with `type`, `types[]`, `created` filters) and `GET /v1/events/{id}` — the first resource module; it establishes the module pattern: `export const routes = [...]`, handlers pure w.r.t. `ctx`.
- Tests: form round-trip with the harness's `encodeForm` (import from `src/bench/run.ts`), auth errors, unknown route, unknown param (top-level and nested), integer coercion error, idempotency replay/mismatch (including replay of an error), list pagination/limit errors/created filter, search query parsing, expand (single, list `data.` path, too deep), `Parity-Now` controls `created`, events list after a seed + a fake emitting handler, reset under 50 ms.

## Task 3: Behavior modules A — customers, products, prices, payment methods

**Paths:** `src/twin/resources/customers.ts`, `src/twin/resources/products.ts`, `src/twin/resources/prices.ts`, `src/twin/resources/payment_methods.ts`, `src/twin/cards.json`, `src/twin/errors.json`, `test/twin-resources-a.test.ts`
**Depends on:** Task 2.

- Customers: create/retrieve/update/delete/list (`email`, `created`, pagination)/search; tombstone behavior (retrieve deleted → 200 `{id, object: "customer", deleted: true}`; update deleted → 400 `resource_missing` param `id`); `invoice_settings.default_payment_method` validation (must be attached to the customer); events `customer.created`, `customer.updated` (with `previous_attributes`), `customer.deleted`.
- Products: create/retrieve/update/list (`active`, `created`). Events `product.created`, `product.updated`.
- Prices: create (with `product` or `product_data` → creates the product and emits `product.created`), retrieve/update (`active`, `metadata`, `nickname`, `lookup_key`)/list (`product`, `active`, `type`, `currency`); recurring validation (interval ∈ day/week/month/year → else the observed 400 with no code; `unit_amount` non-negative integer); legacy events `plan.created`/`plan.updated` alongside `price.created`/`price.updated` for recurring prices (see validation notes).
- Payment methods: `cards.json` = test token table from Stripe's public testing docs (`pm_card_visa`, `pm_card_mastercard`, `pm_card_amex`, `pm_card_chargeCustomerFail`, `pm_card_chargeDeclined`, `pm_card_visa_chargeDeclined`… with brand, last4, funding, country and a `behavior` ∈ `ok | attach_declined | charge_fails`). Attach a token → creates a new `pm_…` card payment method attached to the customer (event `payment_method.attached`); attach of an `attach_declined` token → 402 `card_error` `card_declined` with `decline_code`; detach (event `payment_method.detached`); retrieve; list by `customer` (optional `type`) and `GET /v1/customers/{c}/payment_methods`.
- Use `build(type, …)` for every object; add catalog keys for every error (real status/type/code/param; placeholder message).
- Tests: each template flow #1–#4 and #11/#12 (errors) reproduced in-process with the expected statuses and event types from `docs/plan/impl/templates-validation.md`.

## Task 4: Behavior modules B — subscriptions, invoices, payment intents, charges, refunds

**Paths:** `src/twin/resources/subscriptions.ts`, `src/twin/resources/invoices.ts`, `src/twin/resources/payments.ts` (payment intents + charges), `src/twin/resources/refunds.ts`, `src/twin/billing.ts` (shared: period math, invoice creation, payment attempt), `src/twin/errors.json`, `test/twin-resources-b.test.ts`
**Depends on:** Task 3.

- Subscription create: `items[]` with `price` (or `price_data`), `quantity`; `default_payment_method` or customer's `invoice_settings.default_payment_method`; `payment_behavior` ∈ `allow_incomplete` (default), `default_incomplete`, `error_if_incomplete`, `pending_if_incomplete`; `collection_method` (`charge_automatically` default, `send_invoice` + `days_until_due`); `cancel_at_period_end`; `metadata`. On dahlia `billing_mode` defaults to `{type: "flexible", flexible: {proration_discounts: "included"}, updated_at}` and `current_period_start`/`current_period_end` live on **subscription items**, not the subscription. Calendar-correct period end (month/year intervals add calendar months; day-of-month clamping).
- First invoice: created, finalized (`draft`→`open`), line items per item, `amount_due`/`amount_paid`/`amount_remaining`, `subtotal`/`total`; payment attempt for `charge_automatically`: good card → payment intent `succeeded` + charge `succeeded` + invoice `paid`, subscription `active`; `charge_fails` card → `allow_incomplete`/default: subscription `incomplete`, invoice `open`, PI `requires_payment_method`, charge `failed`; `error_if_incomplete` → 402 `card_error` `card_declined` and nothing persists (see validation notes for the exact error body keys and event set); `send_invoice` → invoice `open`, no payment, subscription `active`. `latest_invoice` = invoice id. Emit the event set observed in the validation notes for each branch (`customer.subscription.created`, `invoice.created`, `invoice.finalized`, `invoice.paid`, `invoice.payment_succeeded`, `payment_intent.created`, `payment_intent.succeeded`, `charge.succeeded`, `customer.updated`, …); where the notes are silent, consult the oracle recordings of templates #5–#15 in `recordings/` if present, else choose the Stripe-documented set and list it under concerns.
- Subscription retrieve/list (`customer`, `status`, `price`, `created`)/update (`cancel_at_period_end` → sets/clears `cancel_at` = item `current_period_end`; `metadata`; `default_payment_method`; `description`) — item/price/quantity changes and proration are **W4**, return 400 `parity: not_implemented` via a catalog key for now; cancel (`DELETE`) → `status: canceled`, `canceled_at`, `ended_at`, `cancellation_details`, event `customer.subscription.deleted`; cancelling an already-canceled subscription → 404 `resource_missing`.
- Invoices: retrieve, list (`customer`, `subscription`, `status`, `created`). Pay/void/finalize/create_preview are W4 (catalog `not_implemented`).
- Payment intents and charges: retrieve, list (`customer`, `created`); charge `amount_refunded`, `refunded`, `refunds` sub-list if the schema requires it; `payment_intent.latest_charge` = charge id.
- Refunds: create (`payment_intent` or `charge`, `amount` optional → full remaining), validations: amount > refundable → 400 no code, param `amount`; negative/zero → `parameter_invalid_integer`; fully refunded → 400 `charge_already_refunded`; `status: succeeded` synchronously; updates charge (`amount_refunded`, `refunded`); events `refund.created`, `charge.refunded`, plus others observed; retrieve; list (`payment_intent`, `charge`).
- Tests: templates #5–#10, #13–#15 flows in-process with expected statuses and event types; period-end calendar math (Jan 31 + 1 month → Feb 28/29).

## Task 5: Webhook endpoints and delivery

**Paths:** `src/twin/resources/webhook_endpoints.ts`, `src/twin/webhooks.ts`, `src/twin/errors.json`, `test/twin-webhooks.test.ts`
**Depends on:** Task 2 (independent of Tasks 3–4 except the shared catalog file).

- CRUD for `webhook_endpoints` (`url`, `enabled_events` incl. `*`, `description`, `metadata`, `disabled` on update); `secret` (`whsec_…`) returned only on create; delete → tombstone body.
- Delivery: after each `store.apply`, for every enabled endpoint whose `enabled_events` matches, POST the event JSON with header `Stripe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<payload>" with the endpoint secret>`; non-2xx or network error → retry up to 3 times with backoff (twin default 1 s, 5 s, 25 s; configurable via `createTwin({ webhookBackoffMs })` for tests). Delivery is asynchronous and never delays the API response. `event.pending_webhooks` decrements on success.
- Tests: signature verifies with an independent HMAC computation; retry then success against a local receiver; `*` matching; no delivery to disabled endpoints.
