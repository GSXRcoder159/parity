## Reading (added by hand after the run)

Run `20260929T000125-yu6f`, started 00:01 UTC on 2026-09-29 because of the daily LLM cap (the file name keeps the
brief's `2026-09-28-h4-80`). The 60 new tasks were written before any twin or sandbox result for them, and the scripted
agent passes all 60 on the sandbox (after one setup fix) and on the twin (`evals/h4/README.md`, Status).

- **Verdict: inconclusive (90–95%).** Twin vs sandbox 75/80 = 93.8%, Wilson 95% CI 86.2%–97.3%. The CI is narrower
  than the 20-task 83.9%–100.0% but still spans the 90% stop line and the 95% confirm line. The control (twin vs a second
  twin run) is 76/80 = 95.0%, CI 87.8%–98.0%, so the noise floor is 5.0%: the H4 disagreement rate (6.2%) is about the
  agent's own run-to-run rate. The control run and the sandbox run agree on 77/80 (96.3%), so the H4 number moves by
  about 2.5 points with which twin run it is paired against.
- **All 5 disagreements are in one family:** the 12 tasks that need `cancel_at_period_end` (end at period end,
  reactivate, and their combinations). That parameter is not in the ported `update_subscription` tool schema, so the
  model has to add it unprompted, or cancel now, or stop. In this family twin vs sandbox is 7/12 and twin vs control is
  8/12. On the other 68 tasks both are 68/68 (CI 94.7%–100.0%), including all 8 `invoice-*`, all 10 `lookup-*` and all
  4 `preview-*` tasks. That is a slice picked after seeing the result, so it describes the result; it is not the H4
  number.
- **Each disagreement, attributed with the control:**
  - `cancel-at-period-end` (twin fail, control pass, sandbox pass): **agent variance.** The twin passes the same task on
    its control run. On the twin run the agent stopped after 3 model calls without setting the period end.
  - `reactivate-addon-only` (twin fail, control pass, sandbox pass): **agent variance.** The twin passes it on the
    control run. On the twin run the add-on was still set to end at period end.
  - `reactivate-and-upgrade` (twin fail, control pass, sandbox pass): **agent variance.** The twin passes it on the
    control run. On the twin run the plan change was made without an immediate invoice (the latest invoice is still the
    `subscription_create` one): a parameter the agent chose.
  - `cancel-all-at-period-end` (twin pass, control pass, sandbox fail): **agent variance, probable.** The control
    cannot show variance on this task, because both twin runs pass. On the sandbox the agent stopped after 3 model calls
    without writing, and the scripted agent passes the task there, so the sandbox supports a pass. What the agent read
    before stopping is not logged.
  - `cancel-addon-at-period-end` (twin fail, control fail, sandbox pass): **agent variance, probable; not shown.** On
    both twin runs the agent canceled the add-on now; on the sandbox it set the period end. The twin answers the
    scripted call (`update_subscription` with `cancel_at_period_end`) correctly, so it supports a pass. The harness does
    not log tool inputs, so a twin answer to some other input that led the agent to cancel now cannot be ruled out. The
    family's twin-vs-control rate (4/12) makes a fail on both twin runs by chance plausible.
- **Stated before the run, not seen:** the twin's `parity: <key>` error messages did not produce a disagreement. All 8
  tasks whose scripted solution hits an error path (over-refund, a refunded charge, a canceled subscription) pass on
  all three runs.

  happens (the known twin gap, `TWIN_GAPS`); on the sandbox the swap succeeds and the task fails its invoice check (the
