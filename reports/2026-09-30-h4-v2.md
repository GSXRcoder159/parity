### The one disagreement, attributed with the tool keys

- `preview-seats-within-limit` (twin pass, control pass, sandbox fail): **agent variance, probable; the control cannot
  show it, because both twin runs pass. A difference in what the agent read is not excluded.**
  - **Same write on every run.** The key sequences are:
    - twin: `list_customers(email)` > `list_subscriptions(customer, status)` > `list_invoices(customer, limit)` >
      `update_subscription(subscription, items, proration_behavior)` > `list_invoices(customer, limit)`;
    - control: the same without the first `list_invoices`;
    - sandbox: the same as the twin, except that the first `list_invoices` had no `limit`.
  - **What failed.** The sandbox run passed the first check (3 seats) and failed the second: the latest invoice is still
    the `subscription_create` one, so no invoice was made for the change.
  - **Why that is the agent's choice.** The instruction's arithmetic has one answer. 2 seats at $20/month, on a
    subscription that started seconds before, prorate to at most $40, within the $45 approval, so the right call is
    `proration_behavior=always_invoice`. That call (the scripted solution) passes this task on the sandbox (the
    2026-09-28 ground truth) and on the twin. v1's LLM agent passed it on all three runs. So on the sandbox the agent sent
    another `proration_behavior` value, which makes the change without an immediate invoice. The divergence is in the
    agent's decision, not in the API's answer to the same call.
  - **Not excluded.** Something the agent read on the sandbox, and that the twin renders differently, may have led to
    that decision. Values are not logged (decision 0001 C3), so what it read and which value it sent are not known.
  - **Test.** A few sandbox reruns of this task, about 6 GETs and $0.05 each. A twin-only rerun cannot show it, because
    both twin runs pass.

### Other observations from the tool keys

  sent `update_subscription(subscription, items, proration_behavior, billing_cycle_anchor)`.
  - On the twin, the task passes only with the anchor set to `now`: the twin implements the interval swap only with
    that value.
  - On the sandbox, the checks passed (the new price is on the subscription, and the latest invoice is a paid
    `subscription_update` one). This is the first observation of the real API on this task with an anchor sent. The
    value it sent is not logged.
  - The twin's gap (a swap without the anchor answers `not_implemented`) is unchanged. The scripted solution sends no
    anchor, still fails on the twin, and stays in `TWIN_GAPS`; template #31 scores that gap for the assisted pass. v2's
    pass means the agent avoided the gap, not that the gap is closed.
- **`billing_cycle_anchor` on other tasks.** The twin and control runs also sent it on 5 other task-runs:
  `upgrade-next-invoice` and `upgrade-no-proration` (twin); `upgrade-no-proration`, `downgrade-no-proration` and
  `preview-upgrade-within-limit` (control). The sandbox run sent it only on `switch-to-annual`. All of these tasks pass
